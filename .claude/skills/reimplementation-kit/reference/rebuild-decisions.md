# Rebuild decisions (RBD-1..RBD-106)

> Licence note: the decisions below describe observable behaviour of lago-api (AGPL-3.0) at pin `591ae90` and of
> the Lago events-processor at tree `83e012866f29` in neutral form; no reference source is reproduced. Read
> `legal-and-provenance.md` before a proprietary rebuild.

A **rebuild decision** (RBD) records one place where the reference behaves in a way a rebuild must consciously
reproduce or change: a defect, a binary floating-point island, a store or mode difference, an undefined order, or a
documented divergence. The `compat` profile reproduces the reference at the pin, quirk included; the `corrected`
profile applies the decision. This chapter is the defining home of every `RBD-n` id: chapters and vectors cite the
ids, and a vector's `rbd` array points here.

## 1. How to read the tables

| Column | Meaning |
|---|---|
| RBD | the decision id (never reused) |
| Behaviour at the pin | what the reference does, stated neutrally |
| Evidence | how the behaviour was established: EXECUTED (the reference produced it at the pin: oracle adapter, green spec example, scenario replay, Go reference binary or Go unit level), RECOMPUTED (independent model), code-read (read only, no vector can show it). The executed artefacts are the non-twin ids of the Vectors column (twins `…x` are RECOMPUTED by definition); the reference locations are the RBD's row in the Provenance section |
| Compat | what a `compat` implementation does (`KEEP` = reproduce the behaviour at the pin) |
| Corrected | what a `corrected` implementation does (`KEEP` = the same as compat) |
| Ruling | `decided` or `proposed` (below) |
| Vectors | unit vectors, scenarios (`scn.*`) and events-processor suite scenarios (`EPC-nn`) that exercise the decision, twins (`…x`) included |

Rulings:

- **decided**: the corrected expectation is settled. Either the owner ruled (OD-2: the events-processor delivery
  contract ADR-001; OD-3: exact decimals and columnar-schema changes are acceptable), or the decision is `KEEP`
  (corrected = compat: no defect, or a documented divergence a rebuild keeps), or a grading convention that holds
  in both profiles, or the correction is the single obvious fix of a plain defect. Vectors and assertions of a
  decided RBD are graded in both profiles.
- **proposed**: the owner has not ruled yet (owner question batch OD-21). The corrected twin vectors and corrected
  suite assertions carry `ruling: proposed`; kitrun and run-suite report them as UNRULED and never grade them. When
  the owner rules, the twins flip to `decided` (or are deleted when the ruling keeps the reference behaviour) and
  this table changes in the same commit.
- A `proposed` row whose only vectors are `both` (no twin yet) pins the reference behaviour; if the owner rules a
  change, those vectors become `compat` vectors and get corrected twins.
- A `both` vector that cites an RBD next to corrected twins of the same op is a profile-neutral control: its input
  avoids the case the decision changes, so the corrected rule expects the same value (KEEP for that detail). The
  row's Corrected column names such controls.
- A twin can cite several RBDs (its `rbd` array lists every decision its input touches); it is `proposed` when any of
  them is. Examples: `clock.jobs_due.001x` (RBD-79 proposed, RBD-94 decided), `ep.parse_timestamp.005x` (RBD-18
  proposed, RBD-15 decided), the RBD-106 twins (also citing the decided RBD-75).

Choosing a profile: a migration that must keep producing the same invoices and records implements `compat`; a
greenfield system implements `corrected` (decided rows) and treats `proposed` rows as advice. Mixed builds are
possible per area, but a component is graded in one profile at a time (`acceptance-and-grading.md`).

## 2. Events-processor delivery and accounting (RBD-1..RBD-12)

in-advance output and the refresh flag; downstream idempotency by `transaction_id`. Full rules:
`events-processor-spec` reference/delivery-and-failures.md.

## 10. Notes on selected decisions

- **Delivery (RBD-1..RBD-12).** The compat goldens record today's losses so a migration can prove it reproduces
  them, never so a rebuild keeps them. A corrected implementation that skips the in-place retry budget and goes
  straight to a delayed retry topic fails `all_done` in the current suite (the suite does not yet seed or observe a
  retry topic: KQ-1, owner question OD-22).
- **Value text (RBD-13, RBD-14, RBD-26).** The billing side parses the enriched value as a decimal; the corrected
  value text is exact so that the columnar store, given an exact column (OD-3), agrees with the relational store.
- **Division by zero (RBD-37).** Severity is high: a tenant-configurable expression plus one crafted event fails every
  ingestion request that evaluates it and blocks an events-processor partition in an abort-restart loop. The compat
  side is not gradable (an internal error and a process abort), so only corrected vectors exist; they stay UNRULED
  until the owner rules.
- **Float islands (RBD-96).** Compat island vectors compare with `float64` or carry the exact 16-digit text; `both`
  vectors near islands compare at a scale both arithmetics reach. The coercion rule is a property of the reference
  runtime and decimal library: a runtime bump re-mints every island vector (KQ-35). The projection period ratio
  (billing-engine-spec BE-PR-41) is a binary64 island outside this umbrella: it stays binary64 in both profiles
  (`pricing.projection.009` is `both`).
- **Split-plan termination (RBD-103).** The compat windows are executed; the resulting second billing and the
  unbilled days are a consequence of the duplicate guard looking only inside the invoice being built. A deployment
  whose server process runs in a zone other than UTC moves the 00:00 test point accordingly; the kit assumes UTC.
- **In-advance quirks (RBD-100, RBD-101).** Both make the sum of in-advance fees disagree with the period total
  computed for the same events. RBD-100 has no twin yet; its compat vectors carry a note with the corrected numbers.
- **Credit-note offset (RBD-106).** The twins were recomputed with the cent on the requested field; refund status
  and balances follow from the corrected amounts.
