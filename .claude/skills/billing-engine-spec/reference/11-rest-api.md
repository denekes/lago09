# 11 — REST API v1 (BE-API)

> Licence note: this chapter describes observable behaviour of lago-api (AGPL-3.0) at pin `591ae90` (2026-09-08).
> It is a behavioural specification written fresh from executed vectors and probes, not source code. Proprietary
> clean-room rebuilds should have it reviewed (`reimplementation-kit/reference/legal-and-provenance.md`).

Facts as of lago-api `591ae90`. This chapter specifies the public HTTP surface of the billing engine: versioning,
authentication and the API-key permission model, request and response envelopes, the exact error bodies, pagination
and its count cache, the endpoint table of the in-scope resources with their permission resources and typed request
roots, and the response field catalogue that the scenario tier snapshots
(`reimplementation-kit/reference/scenario-tier.md`). What each endpoint computes belongs to the business chapters
(01-10); webhooks are chapter 12, the clock chapter 13, out-of-scope surfaces chapter 14.

Reading guide: rules are numbered `BE-API-n`; every rule line ends with `[vec: …]` naming the vectors that pin it
(file `billing-engine-spec/vectors/api.jsonl`, scenarios `scn.*`) or a prose-only marker with the reason. Op schemas:
`reimplementation-kit/schemas/ops/api.*.schema.json` (each description restates its rule in one paragraph). Body
texts in this chapter are exact: compact JSON, keys in the order shown.

## 1. Base URL, versions, transport

- **BE-API-1** The API lives under `/api/v1`; `/api/v2/…` paths that are not part of the newer product catalogue answer exactly like their `/api/v1` twin (same handlers, same payloads). Every response is JSON whatever the `Accept` header. `GET /health` (database ping: `200 {"version","github_url","message":"Success"}`, or `500` with `"message":"Unhealthy"`) and `GET /ready` (`200 {"status":"ok"}`, `503 {"status":"shutting down"}` while draining) need no key. Every `update` route accepts PUT and PATCH. [vec: none (prose only: routing table; the scenario tier drives every in-scope route through /api/v1)]
- **BE-API-2** Any unmatched path or method answers `404 {"status":404,"error":"Not Found","code":"resource_not_found"}` without authentication. [vec: api.error_body.014]

## 2. Authentication and permissions

- **BE-API-3** Every `/api/v1` request carries `Authorization: <scheme> <key>`. The header value is split on runs of whitespace (leading whitespace ignored) and the key is the **second** token; the scheme word is not checked (`Bearer k`, `Token k` and `Basic k` all present key `k`), extra tokens are ignored, and a value with a single token (a bare key) presents no key (RBD-88). [vec: api.auth_token.*]
- **BE-API-4** No key, an unknown key or an expired key answers `401 {"status":401,"error":"Unauthorized"}`. A key is usable while its `expires_at` is null or strictly later than now (at the exact instant it is already rejected). [vec: api.error_body.013]
- **BE-API-5** A key belongs to exactly one organization; every lookup (by code, external id or id) is scoped to it, so another organization's object answers the resource's `404 …_not_found` (BE-API-15). [vec: none (prose only: tenancy is a property of every scenario, each runs in its own organization)]
- **BE-API-6** Permissions: the request mode is `read` for GET and `write` for every other method. The check runs only when the organization has the premium integration `api_permissions` **and** the premium licence is active; the key's `permissions[<resource>]` must then contain the mode, else `403 {"status":403,"error":"Forbidden","code":"<mode>_action_not_allowed_for_<resource>"}`. Without the integration (or without the licence) every key may do everything. A key created without explicit permissions holds every resource with both modes. Resource names used by the in-scope endpoints (the resource of each endpoint is the "Perm." column of section 8): `add_on`, `alert`, `applied_coupon`, `billable_metric`, `billing_entity`, `coupon`, `credit_note`, `customer`, `customer_usage`, `event`, `fee`, `invoice`, `lifetime_usage`, `organization`, `plan`, `subscription`, `tax`, `wallet`, `wallet_transaction`, `webhook_endpoint`, `webhook_jwt_public_key`. [vec: api.authorize.*]
- **BE-API-7** The four event-ingestion endpoints (`POST /events`, `/events/batch`, `/events/estimate_instant_fees`, `/events/batch_estimate_instant_fees`) may resolve the key from a cache kept at most one hour and never past the key's expiry; a key found expired in the cache is looked up again. Every endpoint except single-event ingestion records the key's "last used" instant (persisted hourly by the clock), and every mutation except event endpoints is written to an audit log (chapter 14). [vec: none (prose only: caching is a performance detail invisible to a single request; expiry semantics are BE-API-4)]

## 3. Requests

- **BE-API-8** Write bodies are JSON objects wrapping the resource under a root key (`{"customer": {…}}`, `{"plan": {…}}`; the root of each endpoint is in section 8). A missing root, a blank one or a root that is not an object answers `400 {"status":400,"error":"BadRequest: param is missing or the value is empty or invalid: <root>"}`. [vec: api.error_body.012]
- **BE-API-9** Keys inside the root that the endpoint does not list are silently ignored (each endpoint has an allow-list, section 8); nested lists of objects keep only their listed keys. One exception keeps a raw value so that validation can reject it: a non-array `event_types` of a webhook endpoint (chapter 12). [vec: none (prose only: ignoring unknown keys has no output; the webhook exception is pinned by webhooks.normalize_event_types.004)]

## 4. Responses

- **BE-API-10** A single object is returned as `{"<root>": {…}}`; a list as `{"<plural>": […], "meta": {…}}` where `meta` (section 6) is present on paginated index endpoints only (batch event ingestion, wallet-transaction creation, batch alert creation and the billing-entity list return a bare list without `meta`). [vec: none (prose only: envelope shape is asserted by every scenario step; scn.*)]
- **BE-API-11** Every successful mutation answers `200` with the object (no 201/204), including DELETE, which returns the deleted, terminated or voided object as it is after the operation (RBD-89). Exceptions answering `200` with an empty body: e-mail resend, payment retry, and document download when the document does not exist yet (an asynchronous generation is started; chapter 14); deleting all alerts of a subscription or of a wallet. [vec: none (prose only: status codes of mutations are asserted by scenario steps, e.g. the DELETE step of scn.subscription.terminate.003)]
- **BE-API-12** Encodings in responses (RBD-87, RBD-89; the type of every field is in section 9): minor-unit amounts (`*_cents` fields whose name does not contain `precise`), counts and sequence numbers are JSON integers; exact decimals are JSON **strings** in plain fixed-point notation with at least one fractional digit and never an exponent (`"1.0"`, `"3.50123"`): units, credits, conversion rates, alert values, every field whose name contains `precise` (fee `sub_total_excluding_taxes_precise_amount_cents` included), and the fee's `precise_amount`, `precise_total_amount` and `taxes_precise_amount` (its precise cents divided by the currency's minor units per major unit); values the reference holds in binary floating point are JSON **numbers** spelled as in chapter 12 BE-WH-12 (`20.0`): tax rates, every `taxes_rate`, plan `trial_period`, lifetime-usage `completion_ratio`; dates are `YYYY-MM-DD`; instants are UTC whole seconds `YYYY-MM-DDTHH:MM:SSZ` except five millisecond fields written `…SS.mmmZ` (subscription `started_at`, event `timestamp`, wallet `terminated_at`, invoice `payment_dispute_lost_at`, lifetime-usage threshold `reached_at`) and the fee's `from_date` / `to_date`, written in whole seconds with a numeric offset `…SS+00:00`. Counter fields kept for compatibility (`active_subscriptions_count`, `draft_invoices_count`, `plans_count`, `customers_count`, tax `*_count`) are always `0`. Strings are escaped as in BE-API-17. [vec: none (prose only: the kit's numeric comparison accepts a JSON number where a decimal string is expected, so no vector can pin a JSON type; every type of section 9 was observed by serialising each object through the reference, see Provenance)]

## 5. Errors

Every error body is compact JSON with keys in this order: `status`, `error`, `code`, then `error_details` (or
`provider`). The HTTP status equals `status`.

| Failure | HTTP | Body |
|---|---|---|
| resource not found | 404 | `{"status":404,"error":"Not Found","code":"<resource>_not_found"}` |
| operation not allowed in the object's state | 405 | `{"status":405,"error":"Method Not Allowed","code":"<code>"}` |
| validation | 422 | `{"status":422,"error":"Unprocessable Entity","code":"validation_errors","error_details":{"<field>":["<code>",…]}}` |
| forbidden (feature, permission, store) | 403 | `{"status":403,"error":"Forbidden","code":"<code>"}` |
| unauthorized (raised by an operation) | 401 | `{"status":401,"error":"<message>"}` |
| lock not acquired | 422 | `{"status":422,"error":"Unprocessable Entity","code":"<code>"}` |
| third-party failure | 422 | `{"status":422,"error":"Unprocessable Entity","code":"third_party_error","error_details":{"third_party":…,"thirdparty_error":…}}` |
| provider throttling | 429 | `{"status":429,"error":"Too Many Provider Requests","code":"too_many_provider_requests","error_details":{"provider_name":…,"message":…}}` |
| payment-provider failure (chapter 14) | 422 | `{"status":422,"error":"Unprocessable Entity","code":"provider_error","provider":{"code":…},"error_details":{…}}` |
| missing root | 400 | BE-API-8 |
| no/unknown/expired key | 401 | BE-API-4 |

- **BE-API-13** The error bodies are exactly those of the table (key order included). [vec: api.error_body.001, api.error_body.002, api.error_body.003]
- **BE-API-14** Validation details map each field to the list of error codes in check order (codes are snake_case words such as `value_is_mandatory`, `value_is_invalid`, `value_already_exist`, `invalid_format`, `url_is_invalid`). A single business-rule rejection uses the same shape with the field `base` unless the operation names a field (`{"base":["subscription_canceled"]}`, `{"activation_rules":["subscription_not_pending"]}`). [vec: api.error_body.003, api.error_body.005]
- **BE-API-15** Not-found codes are `<resource>_not_found` with the singular resource name (`billable_metric_not_found`, `plan_not_found`, `customer_not_found`, `subscription_not_found`, `invoice_not_found`, `charge_filter_not_found`, `billing_entity_not_found`, …). Show endpoints answer it themselves; update and delete endpoints answer it from the operation, with the same body. [vec: api.error_body.001]
- **BE-API-16** A forbidden failure without an explicit code uses `feature_unavailable` (premium-gated features). An unauthorized failure raised by an operation carries its message, by default the lower-case `"unauthorized"` — distinct from the authentication failure of BE-API-4 (`"Unauthorized"`). [vec: api.error_body.007]
- **BE-API-17** A lock-acquisition failure answers 422 with code `lock_acquisition_failed` by default; third-party and throttling failures as in the table. Strings in every response body, error bodies included, are escaped like webhook bodies (`<`, `>`, `&` as `\u003c`, `\u003e`, `\u0026`; chapter 12 BE-WH-12). [vec: api.error_body.008, api.error_body.009]
- **BE-API-18** Any other operation failure is not mapped: the request fails with HTTP 500 and a body that is not part of the contract. [vec: api.error_body.011]
- **BE-API-19** Batch endpoints report validation errors per element keyed by the element's array index as a string: `{"error_details":{"1":{"timestamp":["invalid_format"]}}}` (chapter 02). [vec: none (prose only: batch event validation is pinned by the events.validate_batch vectors of chapter 02)]
- **BE-API-20** Bodies outside the envelope: invoice preview with a non-array `coupons` answers `400 {"status":400,"error":"coupons_must_be_an_array"}`, with a non-object `subscriptions` `400 {"status":400,"error":"subscriptions_must_be_an_object"}`; the enriched-events listing (event-store variant only) answers `403 …"code":"endpoint_not_available"` for an organization on the relational store and sets the header `X-Lago-Endpoint-Status: beta` on success. [vec: none (prose only: preview and the enriched listing are not part of the unit or scenario tiers)]

## 6. Pagination and listing

Index endpoints take the query parameters `page` and `per_page`.

- **BE-API-21** Parameter reading: `page` is the integer prefix of its text, read leniently (leading whitespace and a sign accepted: `" 2"`, `"+2"` and `"2.9"` → 2; no digits → 0); absent or below 1 → 1. `per_page` absent → **100**; a value starting with a digit → its leading integer (`"10x"` → 10, `"0"` → 0); any other value, including a negative one → **25**. There is no maximum. The page holds records `(page − 1) × per_page + 1 … page × per_page` of the ordered list. [vec: api.pagination_meta.001, api.pagination_meta.005, api.pagination_meta.006, api.pagination_meta.007]
- **BE-API-22** `meta = {"current_page","next_page","prev_page","total_pages","total_count"}`. With N = total_count > 0: `total_pages = ceil(N / per_page)`, `next_page = page + 1` if `page < total_pages` else null, `prev_page = page − 1` if `page > 1` else null, `current_page = page`. With N = 0: `current_page 0`, `total_pages 0`, `next_page` and `prev_page` null. [vec: api.pagination_meta.001, api.pagination_meta.002, api.pagination_meta.003]
- **BE-API-23** A page beyond the last returns an empty list with `next_page: null` and `prev_page = page − 1` (not the last page). [vec: api.pagination_meta.004]
- **BE-API-24** `per_page=0` with at least one matching record is an unhandled failure (HTTP 500); with no record it answers the empty first page of BE-API-22. The corrected profile answers a validation error on `per_page` instead (RBD-86, proposed). [vec: api.pagination_meta.013, api.pagination_meta.013x, api.pagination_meta.014]
- **BE-API-25** Default order of lists: `created_at` descending, then id ascending; some endpoints override it (subscriptions, events by timestamp; chapter of the resource). Clients must not rely on the order of objects created in the same instant. [vec: none (prose only: equal-instant order is not observable deterministically; scenarios compare such lists as sets)]
- **BE-API-26** Count cache (invoices list, customer invoices list, fees list): the total count is cached for 30 minutes under `pagination_count/<invoices|fees>/<sha256-hex>`; the hashed text is the request's permitted parameters without `page`, plus `organization_id`, each object turned into its list of `[key, value]` pairs sorted by key (recursively), serialised as compact JSON. On a request the cached value is used only when it is **greater than** `per_page × page`, where both are read from the raw query as integer prefixes (absent `page` → 1, absent `per_page` → 100, no digits → 0) — not the normalised values of BE-API-21, so with `per_page=abc` or `page=0` any positive cached count is used; otherwise the list is recounted and the cache rewritten. A list can therefore report a stale `total_count` (up to 30 minutes old) on any page but the tail. [vec: api.count_cache_key.001, api.count_cache_key.004, api.pagination_meta.010, api.pagination_meta.011]
- **BE-API-27** The permitted parameters that enter the key: invoices — the scalar filters `amount_from`, `amount_to`, `currency`, `invoice_type`, `issuing_date_from`, `issuing_date_to`, `partially_paid`, `payment_dispute_lost`, `payment_overdue`, `payment_status`, `payment_statuses`, `per_page`, `purchase_order_number`, `search_term`, `self_billed`, `settlements`, `status`, `statuses` and the object `metadata`; array-valued filters (`billing_entity_codes[]`) and unknown keys are **not** part of the key, and the customer of a customer-scoped list is not either, so the organization-wide list and every customer's list with the same query share one cached count. Fees — `fee_type`, `payment_status`, `external_subscription_id`, `external_customer_id`, `billable_metric_code`, `currency`, `event_transaction_id`, `created_at_from/_to`, `failed_at_from/_to`, `succeeded_at_from/_to`, `refunded_at_from/_to`, then `per_page` (null when absent). [vec: api.count_cache_key.002, api.count_cache_key.003, api.count_cache_key.004]

## 7. Natural keys instead of idempotency keys

- **BE-API-28** The API has no idempotency-key header. Repeated requests are de-duplicated only through natural keys: events by `(external_subscription_id, transaction_id)` (chapter 02), customers by `external_id` (`POST /customers` is an upsert: always 200, webhook `customer.created` when new, `customer.updated` otherwise), subscriptions by `external_id` (a second creation with the same id is a plan change, chapter 06). [vec: none (prose only: upsert and duplicate handling are asserted by scenario steps and the events vectors of chapter 02)]

## 11. Edge cases (people get these wrong)

- A bare key in the Authorization header (no scheme) is rejected; any scheme word is accepted (api.auth_token.003, api.auth_token.002).
- `per_page` that is not a number gives 25 per page, not 100 (api.pagination_meta.006); 0 crashes the request when records exist (api.pagination_meta.013).
- An out-of-range page has a `prev_page` but no `next_page` (api.pagination_meta.004).
- The invoices count cache ignores the customer and array filters: two different lists can report each other's total (api.count_cache_key.002, api.count_cache_key.003).
- The service-level unauthorized message is lower-case `unauthorized`; the authentication one is `Unauthorized` (api.error_body.007, api.error_body.013).
- Error bodies escape `<`, `>`, `&` like webhook bodies (api.error_body.009).
- With `per_page=abc` the cache test reads the page size as 0, so any positive cached count is reported (api.pagination_meta.015).
- A fee's `precise_amount` is a decimal string, not a number, while its `taxes_rate` is a number; its `from_date` / `to_date` end in `+00:00`, not `Z` (BE-API-12).
- `pay_in_advance` is required when creating a plan; omitting it is a validation error, not `false` (section 8.1).
